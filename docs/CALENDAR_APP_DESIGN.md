# HIMA — 編集部つきカレンダー（設計メモ）

雑誌アーカイブ（BRUTUS / VOCE / POPEYE / dancyu など）を知識源に、予定の隙間・特別な日・先の予定を埋めるカレンダーアプリ。`calendar/` は依存ゼロのプロトタイプ（データは架空のサンプル）。

## 実行

```bash
cd calendar && python3 -m http.server 8000   # http://localhost:8000
npm test                                      # tests/calendar.test.js（提案エンジン）
```

## 画面

| タブ | 内容 |
|---|---|
| カレンダー | 月表示＋日の予定一覧（追加・削除、localStorage 保存）。選択した日の下に「編集部エージェント」の提案を表示 |
| 提案 | カード形式。右スワイプ＝気になる（保存）／左スワイプ＝違う（次のカード）。デッキが尽きたら variant を進めて別候補で再生成 |
| 保存 | 「気になる」した提案の一覧 |

## 提案ロジック（`calendar/engine.js`）

1. **隙間埋め**：9–21 時で 60 分以上の空きを検出 → 時間帯（朝/昼/午後/夜）に合う雑誌記事をカード化
2. **一日プラン**：予定のない日は朝・昼・午後・夜の 4 スポットを組む
3. **モーメント**：予定タイトルから 会食→手土産、誕生日→贈り物、海/BBQ→海グッズ を検出
4. **2か月先**：45〜90 日先に旅行/デートの予定がなければ、予約リードタイムを理由に提案
5. 選定はタグ一致スコア＋決定的ソート。`variant` で「違う」後の別候補を出す

本番では `ARCHIVE` を雑誌社のアーカイブ検索（ベクトル検索＋権利情報つきメタデータ）に、ルール部を LLM + RAG に置き換える。回答には必ず出典（誌名・号・ページ）を付ける。

## 広告枠の設計

原則：**編集の文脈に溶け込むネイティブ広告。ただし必ず「PR」と明示し、編集提案とは区別する。**

| 枠 | 場所 | 仕組み |
|---|---|---|
| ① インフィード | 提案デッキ | コンテンツ N 枚（初期 4 枚）ごとに 1 枚。直前のカードのタグに近い広告を優先（手土産→菓子店、海→サングラス） |
| ② エージェント提案内 | カレンダーの日別提案の末尾 | その日の提案タグに合うスポンサー枠（1 日 1 枠） |
| ③ モーメント連動（拡張案） | 会食・海・旅行などの予定 | 「手土産」「海グッズ」など、予定の文脈で提案する商品のスポンサー枠（購入/予約導線つき） |
| ④ 提供企画（拡張案） | 提案タブ上部 | 「〇〇提供 今月の特集」として編集部が選んだ企画を冠スポンサー化 |

### ルール
- 広告カードは点線枠＋`PR` バッジ。スワイプで「気になる」にしても保存対象にしない（現状）／スキップ可
- 頻度上限：デッキ 4 枚に 1 枚、同一広告は 1 デッキ 1 回、同一広告主は連続させない
- ターゲティングは予定の「種類（タグ）」のみ。予定タイトルそのものは広告主に渡さない（プライバシー）
- 計測：表示 / スワイプ（興味）/ CTA タップ。「違う」は広告主へのネガティブシグナルとして次回の出稿配分に反映
- 在庫は `ADS`（brand / tags / cta）。本番は広告配信サーバー（枠・予算・頻度制御）から取得
